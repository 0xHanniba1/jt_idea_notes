# 账号密码登录运维说明

本说明适用于 JT Idea Notes 的账号密码版本，配套[实施方案](admin-password-login-plan.md)。账号由管理员开通；邮箱仅作联系与业务通知用途。旧邮箱登录、OAuth、公开注册、API Key 和身份模拟入口已关闭，修改旧环境变量不会恢复这些入口。

本文记录操作方法，不表示已经发布。实施验收使用隔离环境。用户随后授权交付 main 并更新本机 `4180`；发布进度和实际结果记录在 Issue #7，不能把本文步骤当作已完成记录。其他环境仍需对应部署授权。

## 部署前提

- 正式环境使用 `GO_ENV=production` 和 HTTPS。单站点的 `BASE_URL` 必须是浏览器实际访问的完整 HTTPS 来源，包括非默认端口；例如 `https://notes.example.com`。本地 HTTP 仅允许开发环境的 `localhost`、`.localhost` 或回环 IP。
- 反向代理终止 TLS 时，只在 `TRUSTED_PROXY_CIDRS` 中填写实际连接应用的代理 IP/CIDR，多个值用逗号分隔，并在网络层禁止外部绕过代理直接访问应用端口。代理须正确设置并覆盖客户端可伪造的 `X-Forwarded-Proto/Host/For`；未配置可信代理时，应用忽略这些头。不要填全网段，也不要因为代理部署在 Docker 内就信任全部私网。
- 为本部署单独设置 `JWT_SECRET`，通过受限环境文件或部署平台管理；不得沿用公开示例值，不把值写进仓库、命令历史、Issue 或验证报告。CLI 和 Web 应用必须使用同一份经过核对的目标环境。
- 本版按**一个应用/认证进程**部署。登录计数在进程内：每个租户登录名 15 分钟最多 10 次失败，每个来源 IP 15 分钟最多 120 次尝试；密码哈希同时执行最多 2 个，另有最多 16 个等待位置。重启会清空计数，多副本不会共享计数；需要多副本时先实现共享限速，不能只增加副本数。
- 业务页面、JSON API、Feed、附件和导出需要完整登录。业务附件响应使用 `private, no-store`，不能由公开 CDN 缓存，也不能把附件桶设为公开。建议保持 `CDN_HOST` 未设置；如单独加速编译资源，只放行 `/assets/` 与 `/static/assets/`，业务图片、头像和附件仍走本站认证。公开图片例外仅限当前站点的实际 Logo。
- 使用受限访问的环境文件；运行命令时关闭 shell 跟踪，不把完整环境或请求体输出到日志。保留必要的 SMTP 配置，业务邮件仍可发送；无联系邮箱的成员只收到站内提醒。

配置模板见 [`.example.env`](../.example.env)。模板里的数据库是本地开发示例，不是生产目标。

## 命令运行方式

以下命令在包含本版本 `fider` 二进制、`migrations/` 等发布资源的目录执行。示例沿用仓库 Makefile 的 `godotenv -f .env`；`.env` 必须由操作者选择并核对。已有服务管理器注入完整环境时，可直接运行 `./fider account ...`，不要同时加载另一份不明确的配置。

`TENANT_ID`、`USER_ID`、`USERNAME` 是需要替换的占位文本，不是建议使用的账号。ID 必须从目标站点的既有记录精确确认，不能只凭同名或邮箱猜测。命令预览会显示数据库主机、端口、库名及目标租户/用户/角色，不显示数据库连接密码。

每个写命令都先运行同参数 `--dry-run`，核对目标后在真正的交互终端运行写命令。只读预览不读密码、不修改数据库，不锁定稍后写入的状态；写命令会重新检查目标。不要用管道、重定向输入或环境变量传入密码，CLI 不支持密码参数。

真正写入前，CLI 要求输入 `YES`，再以隐藏方式输入临时密码两次。密码为 15–128 个 Unicode 字符、最多 512 字节，允许空格和粘贴，拒绝已列出的常见弱密码。关键目标摘要或终端提示输出失败时会中止；成功信息只会在事务提交后出现。提交后的结果输出失败也会返回非零，此时先核对实际状态，不能盲目重试重置。

账号命令自身不会执行迁移、启动 Web 服务或后台任务。未知账号命令、无 TTY、目标不符或已有凭据等情况返回失败，不会回退为启动服务。

### 为既有用户初始化登录

适用于目标站点与用户都为 active、且该用户尚无密码凭据的情况。首次切换应选择**现有管理员的原用户 ID**，保留历史内容归属和权限；初始化普通用户不会提升其角色。

```sh
godotenv -f .env ./fider account initialize --tenant-id TENANT_ID --user-id USER_ID --username USERNAME --dry-run
godotenv -f .env ./fider account initialize --tenant-id TENANT_ID --user-id USER_ID --username USERNAME
```

登录名会去除首尾空白并转小写，长度 3–32 位，以字母或数字开头，仅包含小写字母、数字、点、下划线和连字符；同一站点内唯一。已有凭据时拒绝覆盖。成功后用户先用临时密码进入强制改密页，设置新密码，再回登录页重新登录。

### 恢复既有管理员密码

```sh
godotenv -f .env ./fider account reset-password --tenant-id TENANT_ID --user-id USER_ID --dry-run
godotenv -f .env ./fider account reset-password --tenant-id TENANT_ID --user-id USER_ID
```

该离线恢复只允许**active 站点上、active 且已经初始化的管理员**。它不会创建账号、改变登录名、提升普通成员角色或解封停用用户。事务内替换临时密码、置待改密并轮换会话 stamp；旧密码及旧完整/受限会话失效。普通成员重置或停用账号恢复应由其他已登录管理员在成员管理页处理，恢复必须同时设置新的临时密码。

未初始化管理员使用 `initialize`，不能用 `reset-password` 代替。如果没有满足条件的管理员，保持维护状态，单独审查恢复路径，不直接修改角色或用户状态来绕过限制。

### 全新空库首次安装

数据库须先完成本版本迁移，`HOST_MODE` 为 `single`，且数据库中**没有任何站点**。

```sh
godotenv -f .env ./fider account bootstrap --dry-run
godotenv -f .env ./fider account bootstrap
```

写命令交互收集站点名称、管理员姓名、登录名及临时密码，并在同一事务创建站点和首位管理员。已有站点时拒绝执行，即使该站点暂时没有可登录管理员；不要清空站点表来强行使用 bootstrap。Web 没有“第一个访问者成为管理员”的安装入口。

## 迁移备份与正式切换

1. **先在隔离副本演练。** 为副本单独分配数据库、端口、环境、Cookie 主机和镜像标识，停用真实邮件/Webhook 出站投递。确认测试配置没有指向正式库或 `4180` 原版数据。`make test-server` 会迁移，数据库测试会 seed，绝不能对正式库运行。
2. **准备可恢复备份。** 固定新旧构建的提交/镜像标识，备份完整 PostgreSQL 数据及对应时点的全部附件（SQL、文件目录或对象存储）。迁移后备份必须包含 `user_credentials`、用户 stamp 及关联数据。管理员页面的普通 `backup.zip` 明确排除密码凭据，不能用它替代完整运维备份。备份按秘密限制访问，并先在隔离副本恢复验证。
3. **取得具体切换授权后停写。** 确认目标实例、数据库、现有管理员 ID、预计停机及回退边界；由反向代理维护页阻断外部流量，停止旧应用和其写入任务。不能让新旧认证应用同时对外处理请求。保留原数据与备份，不通过重建同名用户迁移身份。
4. **执行已演练的新迁移。** 在核对过的目标环境运行下面的迁移命令。迁移会执行所有尚未应用的迁移，需提前查看其清单；本次凭据迁移只追加 `user_credentials`，不会替所有旧用户生成密码。Docker 镜像默认启动命令会先迁移再启动服务器，因此不能把“试启动镜像”当作只读检查。

   ```sh
   godotenv -f .env ./fider migrate
   ```

5. **初始化并核对管理员。** 按前面的 `initialize --dry-run` 和 TTY 写命令，为精确的既有 active 管理员 ID 开通登录。全新安装才使用 bootstrap。至少一位 active 管理员完成初始化后才允许后续开放；否则新应用停在初始化提示，不能临时恢复注册或旧邮箱登录。
6. **完成旧凭据撤销。** 在已审查、授权的切换操作中清除存量 API Key，并统一轮换全站用户 stamp。当前 `migrate` 不执行该全站操作；账号 CLI 只处理指定目标，没有全站批量撤销子命令。应事先准备并在副本验证对应操作，不能把迁移成功误记为已经清理旧凭据。新版对旧 Cookie、旧 API Key 和模拟身份头的拒绝仍由服务端强制执行。
7. **受控启动并验收。** 启动一个新应用进程，先只向操作者开放 HTTPS。管理员完成首次改密、重新登录，检查历史记录/附件、成员管理、普通成员开通、强制改密与重置撤销；确认匿名、旧 Cookie、旧 API Key、邮件和 OAuth 入口均不能进入业务。核对数据库中的用户 ID、角色与内容归属没有意外变化，再开放流量。
8. **记录实际结果。** 将操作对象、构建标识、迁移结果、备份恢复检查、验收证据及剩余问题对应记录；不得包含密码、hash、Cookie 或密钥。代码完成、隔离验证通过、代码合并与真实部署分别记录。

迁移、账号变更或验收失败时保持维护；不要把失败步骤后面的操作继续当作成功执行。

## 恢复与回退边界

- 忘记密码优先由其他管理员重置，或使用本机 `reset-password`；普通成员、停用用户和未初始化用户不能借离线恢复提升权限。
- 不能直接回滚到原 Fider/旧认证构建。旧构建会重新开放邮箱、OAuth 或 API Key 路径，也无法正确处理新建的无邮箱密码账号。保留旧镜像只用于受控分析或副本验证，不是安全的在线回退方案。
- 开放流量后若要回退应用，只能使用仍认识当前凭据表、认证版本并保持旧入口关闭的兼容构建，且先在副本验证。没有兼容构建时保持维护并修复前进，不自动启动旧镜像。
- 恢复数据库备份可能丢失备份后新增业务内容，并恢复旧密码和会话状态。先说明数据与认证影响、取得单独授权，在副本核对恢复结果后再决定是否切换；恢复后应再次检查管理员、会话撤销及附件一致性。
