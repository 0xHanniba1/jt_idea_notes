## 1. 目标与已确认规则

本站供公司内部人员记录想法、问题和优化建议。管理员开通账号，员工用登录名和密码登录，不再依赖邮箱验证码或第三方身份。

| 场景 | 已确认行为 |
| --- | --- |
| 开通账号 | 仅管理员操作；填写自定义登录名、姓名和临时密码；邮箱不必填 |
| 登录身份 | 登录名与显示姓名分开；可用拼音或工号作为登录名 |
| 首次登录 | 临时密码验证成功后，必须先修改密码，才能进入业务页面 |
| 忘记密码 | 联系管理员重置临时密码；再次登录仍须先修改 |
| 主动改密 | 员工验证当前密码后设置新密码 |
| 旧认证 | 停用邮箱验证码、邮件登录链接、第三方登录及其服务端入口 |
| 历史数据 | 保留原用户 ID、角色、记录归属、评论、关注、附件及原有邮箱数据 |
| 切换保障 | 先为现有管理员初始化密码凭据，并提供本机恢复命令，避免管理员无法进入 |

沿用 Go、React、TypeScript、SCSS、PostgreSQL、现有 bus 和角色体系。不接企业微信，不增加公开注册、审批、部门、单点登录、短信/邮件找回密码或定期强制改密。

以下技术规则是本方案的实施默认值，不冒充额外的用户选择：停用旧 API Key 身份入口、密码长度与哈希参数、会话有效期、限速阈值及本机恢复方式。它们服务于本次账号密码认证，不另建通用身份平台。

## 3. 数据结构与输入规则

### 3.1 新增凭据表

追加新迁移创建 `user_credentials`，不修改历史迁移，不重建用户或批量填充默认密码。

| 字段/约束 | 用途 |
| --- | --- |
| `tenant_id`、`user_id`，联合主键 | 一个租户内每个用户最多一份密码凭据 |
| 联合外键引用 `users(tenant_id, id)` | 禁止把凭据绑定到其他租户的同 ID 用户 |
| `username`，租户内唯一 | 规范化后的登录名；停用账号继续占用该名称 |
| `password_hash` | 含算法、版本、参数和盐的 Argon2id 编码值 |
| `must_change_password` | 新建、初始化、管理员重置后为 true；员工成功改密后为 false |
| `created_at`、`updated_at` | 初始化与最近凭据更新的时间 |

凭据 DTO 与通用 `entity.User` 分离，hash 不进入 JSON、SSR props、JWT、前端状态持久化或普通备份。管理列表只额外返回登录名和是否待初始化/待改密。登录名不在记录作者等公共用户对象中无目的传播。

没有凭据行的老用户显示“待开通密码登录”，不能登录。管理员给该用户补填登录名和临时密码，绑定原 ID；不得通过“再建一个同名用户”完成迁移。普通新账号仍由现有用户创建流程的内部能力写入，再在同一事务创建凭据，防止只完成一半。

新账号邮箱保存为空字符串；现有邮箱唯一索引已排除空字符串，不造假邮箱。默认使用文字头像。账号停用不删除历史数据；保留的用户注销/站点删除流程必须同时清理凭据，并执行管理员保护。软删除用户时删除其凭据；不新增账号删除功能或永久保留已删除登录名的规则。

### 3.2 输入及密码存储

- 登录名：3–32 个 ASCII 字符，允许字母、数字、点、下划线、连字符，首位为字母或数字。服务端去除首尾空白、统一小写后校验和查重；数据库唯一约束处理并发重复。本版不提供登录名修改，姓名继续可修改。
- 姓名沿用现有长度与必填规则，支持中文；新建账号默认普通成员，可选原有角色，不引入新的权限等级。
- 临时密码和正式密码统一为 15–128 个 Unicode 码点，最大 512 个 UTF-8 字节；允许空格和中文，不裁剪、不转大小写、不静默截断，不要求机械组合大小写/符号。前后端长度算法一致。
- 新密码不能等于当前临时/正式密码；用本地常见弱密码清单拦截明显弱密码，不调用外部服务传送密码。支持粘贴、浏览器密码管理器及显示/隐藏密码。
- 使用现有 `golang.org/x/crypto/argon2` 的 `IDKey`，默认 Argon2id `m=19456 KiB, t=2, p=1`，每次以 `crypto/rand` 生成至少 16 字节盐，派生 32 字节结果。编码含算法版本和参数；严格限制解析参数，防止畸形存储值触发过量资源消耗，常量时间比较结果。
- 临时密码由管理员填写，不新增固定初始密码。管理员输入的明文只短暂存在于当前表单和请求处理内存，提交成功后清空；服务端不回传明文，不能“查看原密码”，不写 localStorage、日志或审计记录。

密码基线参考 [OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)、[OWASP 认证指南](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) 和 [Go Argon2 文档](https://pkg.go.dev/golang.org/x/crypto/argon2)。本机 20 次串行哈希的中位数约 23 ms、P95 约 29 ms；保留上述参数。此值只代表本机样本，服务器上线前按目标资源复核。

## 4. 认证、改密与会话

### 4.1 登录状态

```text
未登录 ── 正确正式密码 ──> 完整登录 ── 当前密码 + 新密码 ──> 改密成功，重新登录
   │
   └── 正确临时密码 ──> 仅允许改密 ── 新密码 + 确认 ──> 改密成功，重新登录

管理员重置：设置新临时密码 + 要求改密 + 撤销全部旧会话
管理员停用：停用账号 + 撤销全部旧会话；历史记录继续保留
```

首次改密完成后回到登录页，以新密码登录；不自动将受限凭据升级成完整会话。主动改密也退出所有设备，包括当前设备。管理员重置时不能绕过员工必须改密的步骤。

### 4.2 两种明确分离的凭据

1. **完整登录 Cookie**：新名称与新认证版本，JWT 包含租户 ID、用户 ID、用途 `session`、当前 stamp、签发及过期时间；绝对有效期 12 小时，不滑动续期。本版不增加“记住我”设置。
2. **改密 Cookie**：独立名称，用途 `password-change`，绑定相同租户、用户、stamp，有效期 10 分钟。过期后重新输入临时密码；临时密码本身直到改密、再次重置或停用前有效。
3. 两者均为 host-only、`HttpOnly`、显式 `SameSite=Lax`、路径 `/`；正式部署 HTTPS 下必须 `Secure`。本地 HTTP 只限开发环境，不能把本地例外用于服务器发布。每次登录成功先清除两种旧认证 Cookie，再只设置本次对应的一种，防止同一浏览器同时保留 A 的完整会话和 B 的改密身份。检测到两种凭据并存时拒绝混合认证并要求重新登录，不回退选用旧完整会话。退出清除两种凭据及旧 Cookie，清理时域和路径必须匹配。
4. 每次受保护请求从数据库校验用户 active、租户、凭据存在、stamp、认证版本和用途；完整登录额外要求 `must_change_password=false`。缺字段、无 stamp、旧版本、旧 signup/OAuth 凭证均拒绝，禁止回退到旧认证。
5. 受限凭据不能让 `IsAuthenticated` 或角色授权视为完整登录。只允许改密页/提交、退出、必要的无业务数据会话信息和静态资源；请求业务 API 返回明确的认证错误，页面跳转到改密页。
6. 原 Bearer API Key、API Key 生成功能和模拟身份请求头停止生效。切换时撤销存量 key；这意味着旧脚本不能再靠 key 调用本站。本版保留网页正常使用的 JSON API，不另做自动化集成认证。

会话轮换与 Cookie 原则参考 [OWASP 会话管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。本版复用 JWT + 数据库 stamp，不另建全量会话管理平台。

### 4.3 必须在服务端覆盖的边界

- 公司内部模式要求完整登录才能读取首页、路线图、记录/评论、搜索、标签、成员、通知、附件、导出和写入 API。不能因某条路由在旧的“私有站点”检查之前注册而漏过。
- 原 Feed、sitemap 和上传图片直链需要逐项归类：涉及业务数据的响应纳入认证，不再返回公共缓存；登录页使用的站点标识及编译静态资源仍可公开读取。普通成员读取他人数据的现有业务权限保持不变。
- 访问权限页面应明确公司内部访问策略，关闭可重新开放匿名业务访问的控制；保存接口也拒绝重新开放。保留旧配置数据用于兼容，不能让旧 `is_private=false` 绕过本次策略。
- 账号停用复用原用户状态，并将“停用/恢复”扩展到合适的成员角色；恢复弹窗必须同时设置新临时密码，在同一事务中恢复 active、替换 hash、轮换 stamp、置待改密状态。任何一步失败保持停用，旧密码和旧会话都不得复活；不能先恢复后再择机重置。
- 管理员创建、初始化、重置和停用均要求完整登录和管理员权限。原协作者可保留既有成员查看权限，不获得开通或重置权限。管理员不能通过管理接口重置/停用自己；自己的正常改密走个人设置，忘记密码走其他管理员或本机恢复。
- 停用、降级和个人注销在事务中保护最后一个可用管理员；“可用”指 active 且已有密码凭据，待首次改密仍能正常完成登录流程。并发校验必须锁住同一租户的管理员变更边界，不能两人同时操作后都失去管理入口。

### 4.4 事务与并发

- 为认证和账号写入建立小范围的“提交后响应”路径：预先准备响应/JWT，显式提交请求事务成功后才发送成功响应或 Cookie；提交失败必须返回失败。调整 `Context.Commit` 的一次性提交/任务出队标记，使 WebSetup 不会再次提交或重复发送后台任务。不能只在 handler 内多调用一次当前 `Commit()`。
- 慢哈希在持锁前完成；签发前以同一份凭据版本/stamp 重新校验或条件更新。禁止“旧密码校验通过后，读取新 stamp 并签发”，否则重置后的旧密码仍可能获得有效会话。
- 改密用已验证的旧 stamp/密码状态作为原子更新条件；两个改密请求最多一个成功。管理员再次重置后，先前受限凭据不能覆盖新密码。重置、停用、恢复和权限变更在同一事务撤销旧会话。
- 业务写入事务在锁内重验认证版本、当前用户 stamp、active、凭据存在、`must_change_password=false` 和当前角色权限，不能只检查固定的版本号。锁保持至事务提交，避免“请求开始时有效，停用提交后仍写入”。当前小规模部署在业务写入前先取租户 `FOR NO KEY UPDATE` 锁，再取用户认证保护锁并持有至提交；跨用户账号操作也先取得同一租户锁，再按用户 ID 固定顺序锁定 actor/target，统一密码和角色更新的锁顺序。租户锁兼容 SQL 附件服务独立事务所需的外键 `KEY SHARE` 锁，避免上传自阻塞。该实现会串行化同租户的业务写入，未来只有实际吞吐量需要时再缩小锁范围。新的 stamp 以 `crypto/rand` 生成，不复用旧值。
- 撤销语义为撤销提交后不再接受旧凭据，不能撤回已经完成的响应。隔离环境用可控并发测试覆盖登录与重置、改密与重置、重复重置、双改密、相互停用/降级及提交失败。

## 5. 接口与旧入口处理

新增路由沿用 `/_api` 风格，服务通过现有 handler → action/cmd/query → bus → PostgreSQL 组织。以下路由已实现。

| 接口 | 权限及行为 |
| --- | --- |
| `POST /_api/auth/password/signin` | 校验登录名/密码；返回下一步 `signed_in` 或 `password_change_required`，清理旧认证 Cookie 后只设置一种对应 Cookie |
| `GET /password/change-required` | 仅有效改密凭据可进入，不加载业务页面 props |
| `POST /_api/auth/password/complete` | 仅改密凭据；设置新密码、撤销旧凭据并要求重新登录 |
| `POST /_api/auth/password/change` | 完整登录；校验当前密码后改密并退出所有设备 |
| `POST /_api/auth/signout` | 清除全部认证 Cookie；UI 改为提交退出，不用 GET 改变登录状态 |
| `POST /_api/admin/accounts` | 管理员；同一事务创建用户及临时凭据；返回安全的账号摘要 |
| `POST /_api/admin/accounts/:id/initialize` | 管理员；只为尚无凭据的既有用户绑定登录名/临时密码 |
| `POST /_api/admin/accounts/:id/reset-password` | 管理员；重置临时密码、强制改密、撤销会话 |

成员查询、现有封禁/解封和角色变更路由复用并加强服务端约束，不重复造两套状态接口；恢复接口新增必填临时密码，按第 4.3 节原子恢复并重置。登录错误统一为“账号或密码不正确”，不区分不存在、未初始化、停用或错误密码；管理员操作可以明确提示重复登录名或无权限等错误。

| 旧路径/能力 | 处理 |
| --- | --- |
| `POST /_api/signin`、`/_api/signin/newuser`、`/_api/signin/verify`、`/_api/signin/resend`、`/_api/signin/complete` | 停用，不能发送验证码、创建用户或换取会话 |
| `GET /signin/verify`、`/invite/verify`、`/signin/complete`、`/loginemailsent` | 停用；已发出的链接/验证码不再有效；`/signin` 替换为密码登录页 |
| `GET /signup`、`/signup/verify`，`POST /_api/tenants`、`/_api/signup/resend`，子域可用性查询 | 关闭自助建站和注册；初始化只通过本机命令 |
| `/oauth/:provider`、其 `/callback`、`/token`、`/echo` | 停用发起、回调、handoff 兑换和测试入口；既有 provider 配置保留但不生效 |
| `POST /api/v1/invitations/send`、`/api/v1/invitations/sample` | 停用邀请注册及试发；由管理员开通替代 |
| `POST /api/v1/users` | 关闭旧 email/reference 创建方式；新开通仅走上表接口。保留受权限保护的成员 GET 查询 |
| `POST /_api/admin/settings/emailauth`、`/_api/admin/oauth`、`/_api/admin/oauth/:provider/status`，`GET /_api/admin/oauth/:provider` | 不再提供旧认证配置读写；旧环境变量不能重新开启认证 |
| Bearer API Key、`X-Fider-UserID`、`POST /_api/user/regenerate-apikey` | 停用；个人设置移除 API Key 区块 |
| 旧 `/signout` | 不再通过 GET 退出；必要时引导到登录页，不执行状态写入 |

退休接口返回不存在/不支持该方法响应（404；仍有 GET 的 `/api/v1/users` 的 POST 返回 405），不转入新注册流程，不写用户或验证记录。具体状态码在路由测试固定，避免因 middleware 顺序仍触发原 handler。无需删除历史迁移和全部上游 OAuth 库，只清理本次失去用途的运行入口、调用与界面。

`/change-email/verify` 是已登录用户更新联系邮箱，不是登录凭据兑换，保留但只接受完整登录且校验目标用户；`/admin/danger-zone/cancel` 是取消站点删除的能力链接，不签发会话，不误删为邮箱登录。旧邮件登录任务不再被调度，保留业务通知邮件。

## 6. 最小安全措施

- **请求来源**：新登录和所有凭据/账号状态写入要求 JSON 且校验完整同源 Origin（协议、主机、端口），无 Origin 时只接受同源 Referer，两者均缺失或为 `null` 则拒绝。覆盖 POST/PUT/PATCH/DELETE，不以 `Accept: application/json` 当作 CSRF 防护；跨站请求和宽松 CORS 不能放行。
- **可信来源**：来源与 Cookie 安全属性使用配置的站点地址；客户端 IP 默认取真实连接地址。仅对明确配置且网络侧限制的反向代理采信 forwarded 头；不直接信任外部 `X-Forwarded-Host/Proto/For`。新接口请求体在 `WrapRequest` 读取前限为 8 KiB，覆盖 chunked body；非本次接口沿用其合理上传上限。
- **限速**：当前单进程部署使用有界、带过期清理的并发安全内存计数，无需新增 Redis。规范化的“租户+登录名”15 分钟内最多 10 次失败，来源 IP 15 分钟内最多 120 次登录尝试；超限返回通用 429 与 `Retry-After`。同时限制密码哈希并发默认 2、等待队列最多 16，满额直接拒绝，不在事务里睡眠。
- **未知账号**：使用相同参数的固定占位 hash 验证，错误格式和限速键处理与真实账号一致；不存在的账号也计数。计数在进程中原子更新，不随请求事务回滚；输入错误和超大请求在哈希前拒绝。日志不能用用户名作为高基数指标标签。
- **限速边界**：进程重启会清空内存计数，因此本版只按单认证进程交付，部署文档明确记录；不宣称多实例共享限速。若实施环境确认必须多实例，再改用已有 PostgreSQL 存储计数，不在第一版预建分布式组件。
- **敏感信息**：新增凭据操作走 SQL 参数脱敏路径；请求、验证失败、异常栈和前端错误上报均不序列化密码、hash、Cookie 或完整请求体。审计只记录操作人 ID、目标 ID、操作类型、结果和时间，禁止记录旧/新密码。
- **缓存与跳转**：登录、改密、账号管理响应 `Cache-Control: no-store`；不把密码放 URL。登录后跳转只接受站内允许路径，不接受外站地址、协议相对路径或回到旧认证路径。

限速数值是当前小规模内部使用的默认值。验收需覆盖公司共享出口 IP 下正常登录、并发失败、伪造 forwarded 头、超大密码及哈希负载，依据实际结果调整数值并同步本方案。

## 8. 初始化、切换与恢复

### 8.1 本机命令（已实现）

- `fider account initialize --tenant-id <id> --user-id <id> --username <name>`：为明确的既有 active 用户建立凭据；预览 ID/姓名/角色后确认，密码由 TTY 隐藏输入并确认两次。已有凭据时拒绝覆盖。
- `fider account reset-password --tenant-id <id> --user-id <id>`：为已初始化的既有 active 管理员恢复临时密码，置待改密、轮换 stamp、撤销旧凭据。不按模糊邮箱/姓名找人，不自动提升角色或解封。
- `fider account bootstrap`：只处理尚无站点的全新单站点安装，交互输入站点、管理员身份及临时密码；已有站点直接拒绝。不开放 Web “第一个访问者成为管理员”的安装入口。
- 初始化和恢复共用 Web 路径的密码策略、原子更新和日志脱敏；不允许密码命令行参数或环境变量，不提供默认万能账号。非交互环境无 TTY 时明确失败，不悄悄落入明文输入模式；后续如有自动化安装需要再单独设计凭据传递。
- 命令提供只读预览/dry-run；真正写入前明确目标数据库、租户与用户，禁止输出连接密码。真实账号初始化和恢复在获得对应授权后由操作者输入秘密，不把真实密码写进 Issue、计划或聊天记录。

### 8.2 隔离演练与正式切换顺序

1. 在独立开发库和经允许的脱敏副本演练；测试数据库、邮件收件箱、端口、Cookie、镜像与 4180 隔离，禁用真实邮件/Webhook 投递。
2. 在副本追加凭据表，核对没有用户 ID/角色/业务内容被改写；演练现有管理员初始化、首次改密、正常登录和离线恢复。
3. 正式切换前准备固定源码/镜像标识、旧版镜像、完整数据库和附件备份。普通站点导出不含密码凭据；受限运维备份必须包含新凭据表、stamp 与全部关联数据，并验证可恢复。备份文件按秘密管理。
4. 取得更新 4180 及本次真实账号初始化授权后，短暂停写，停止旧应用写入，执行新迁移与既有管理员凭据初始化；不用新建同名账号替代。至少一名 active 管理员初始化成功才允许开放新应用。失败时保持维护状态，不发布一个所有人都无法登录的站点。
5. 以受控切换操作撤销存量 API Key、轮换用户 stamp，启用新认证版本。禁止旧/新认证应用同时对外处理流量。新进程启动时检查已初始化管理员，未满足则仅显示维护/初始化说明，不暴露注册后门。
6. 操作者完成管理员首次改密和新密码登录；检查首页、历史记录/附件、中文设置、成员管理、创建普通测试成员及强制改密。验证匿名、旧 Cookie、旧 API Key、邮件/OAuth 链路都不能进入业务。
7. 对比切换前后用户 ID/角色和业务数据；允许变化的仅是明确列出的凭据、stamp、API Key 及必要认证状态。把实际检查与镜像/提交对应记录到验证文档，再同步 Issue 的验收勾选与部署状态。

### 8.3 回退与避免锁死

- 本次不是可以只替换前端镜像的发布。旧版应用会重新开放已退休的认证，且新建的无邮箱账号无法按旧方式登录，**不能把直接换回旧镜像写成安全、无损回退**。
- 尚未开放流量时若初始化失败，保持维护并修正或撤回未完成步骤；凭据迁移是追加式，不需要删除历史业务表。管理员忘记密码优先走受控恢复命令，而不是回退整个数据库。
- 开放流量后的应用回退只能使用仍支持本次凭据表、认证版本和关闭旧入口的兼容构建；先在副本验证兼容性。没有兼容构建时保持维护、修复前进，不自动重启旧认证版本。
- 恢复完整旧备份可能丢失切换后的新增业务记录，并改变已生效的密码/会话状态；必须单独说明影响并授权，不能静默执行。恢复到副本后先校验身份和认证状态，再决定是否切换。
