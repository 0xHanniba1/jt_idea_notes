# 开发、验收与云端发布

## 发布边界

4184 是开发预览环境，4180 是本地验收环境，云服务器是独立的正式环境。三者各自保存数据，不自动同步。

| 触发条件 | 执行内容 | 不触发的动作 |
| --- | --- | --- |
| 提出修改需求 | 独立分支开发、测试，更新 4184 预览 | 合并 main、更新云端 |
| 明确要求“交付 main，并更新 4180” | 检查、合并 PR、同步 main、更新本地 4180，完成 Issue 和分支收尾 | 更新云端 |
| main 的 push 构建与测试成功 | 自动发布该提交对应的容器镜像 | 连接服务器、运行迁移、修改云端配置 |
| 明确要求“发布到云服务器” | 确定版本，按下文执行一次受控发布 | 用本地数据库覆盖云端数据 |

日常可以多次重复“修改 → 4184 → main → 4180”。验收通过、合并 main、镜像构建成功均不等于云端发布授权。没有自动云端部署任务，也不在 Actions 中保存服务器登录凭据。

## 镜像与版本

自动发布由 [publish.yml](../.github/workflows/publish.yml) 定义，只接受本仓库 main 上成功的 push CI，直接发布该次 CI 已验证过的 `linux/amd64` 镜像，不重新构建。PR、其他分支以及失败或取消的 CI 不发布正式镜像。

镜像名称为 `ghcr.io/0xhanniba1/jt_idea_notes:sha-<完整的 40 位提交 SHA>`。发布时记录镜像 digest，云端 Compose 使用 `ghcr.io/0xhanniba1/jt_idea_notes@sha256:<digest>` 固定内容，不使用可漂移的 `latest` 或分支标签。

这套新流程在相关 PR 合并前尚未启用。首次合并后，须确认 main CI 和镜像发布实际成功、产物可以拉取，才能把该镜像视为可发布版本；只有配置文件存在不能证明发布已完成。镜像发布失败不撤销已完成的代码交付或本地验收，但该版本不能按新流程部署云端。

GHCR 包的可见性和服务器拉取能力须实际确认。私有包使用最小读取权限的凭据；通过标准输入登录，不把凭据写进命令历史、仓库、发布记录或聊天。首次验证拉取应在停机前完成；不可拉取时先解决访问问题，不切换到未经验证的镜像。

可以在本地使用 [release-plan.py](../scripts/release-plan.py) 生成待发布版本清单：

```sh
python3 scripts/release-plan.py <完整的40位提交SHA>
python3 scripts/release-plan.py <完整的40位提交SHA> --output /tmp/jt-release-plan.json
```

该工具只读取 GitHub 构建、发布记录及 main 祖先关系，使用 `release-sha-<完整SHA>` 产物中的 `release.json` 发布凭据；默认将 JSON 输出到终端。它不连接服务器、不部署、不操作数据库，也不构成云端发布授权。其结果用于准备目标版本，不能替代服务器现场检查；发布凭据不可用时不得猜测 digest 继续发布。凭据保留90天，计划文件应与发布记录一并归档；镜像tag不是不可变保证，实际部署始终以凭据中的digest为准。

- 应用采用 host 网络，只监听回环地址 `127.0.0.1:4180`，由 nginx 提供 HTTPS。

## 云端发布步骤

本节仅在用户明确要求更新云服务器后执行。可以提前整理版本和迁移清单，但不得由本地验收或 CI 完成自动进入本节。

1. **固定范围。** 明确目标提交、成功 CI、镜像标签及 digest，记录用户的发布指令。发布版本确定后，后续 main 更新不应改变本次目标。
2. **核查现场。** 读取云端当前镜像和提交、Compose、数据库版本及迁移历史、磁盘空间、应用健康和备份状态。只记录配置摘要，避免输出 `.env` 密钥。与上述历史拓扑不符时先调整计划，不盲目套用旧命令。
3. **审查迁移。** 比较云端当前版本与目标版本之间的全部迁移，明确预期数据变化、旧应用兼容性和失败恢复方式。应用镜像启动时会先执行迁移，不能把“启动新容器”当作无数据库影响的动作。
4. **准备镜像。** 在应用仍可用时按 digest 拉取，验证架构、提交元数据和 digest；保留当前镜像供兼容回退。首次切换 GHCR 时同时核对既有 `pull_policy`；历史配置为 `never`，必须先把目标 digest 拉到本机。
5. **备份。** 暂停应用写入后运行现有备份脚本，保留数据库、Compose、环境文件及 nginx 配置，记录目录与 SHA256。验证归档可读；涉及有损迁移时，先在隔离库验证恢复及迁移。保留当前账号、密码和 JWT 密钥，不重新生成配置。
6. **更新应用。** 只将 Compose 的应用镜像改为已核验的 digest，保留数据库、端口、挂载及其他运行配置。检查 Compose 配置，启动应用并监测迁移结果及健康状态；不执行删除卷或重建数据库操作。
7. **验收。** 核对实际运行提交与镜像 digest；检查 HTTPS、静态资源、登录、权限、记录和已有附件。数据对照须区分迁移预期变化与异常丢失，不能仅以 HTTP 200 或容器 healthy 判断成功。涉及真实账号的验证使用已有授权会话，不擅自重置密码或新增账号。
8. **记录。** 保存下列发布记录，将结果明确标为成功、回退或中止。成功后保留发布前备份和旧镜像，不顺手清理历史数据。

## 失败处理

- 拉取、检查或备份失败：不启动新版本，若已暂停应用则恢复原服务。
- 数据库迁移未开始，或已确认新数据库结构与旧应用兼容：恢复原 Compose 镜像，启动旧应用并重新验收。
- 迁移已改变数据且旧应用不兼容：保持受控维护状态，记录错误与数据库状态，优先评估前向修复。不得假定换回旧镜像即可恢复。
- 恢复数据库会覆盖备份之后的新数据，不做自动恢复。先明确数据损失范围和恢复方案，取得该操作所需授权，再执行恢复并核对。

## 发布记录模板

```text
发布时间与操作者：
用户发布指令 / 目标服务器：
原提交 / 原镜像 digest：
目标提交 / CI 运行链接：
目标镜像标签 / digest / 架构：
待执行迁移 / 预期数据变化 / 旧版本兼容性：
发布前备份路径 / SHA256 / 归档与恢复验证结果：
实际运行提交 / 实际镜像 digest：
健康、登录、权限、记录与附件验收：
结果 / 未解决问题 / 回退情况：
```

发布记录不得包含密码、令牌、Cookie 或完整环境文件。仓库中的开发交付记录与实际云端发布记录分别维护，避免将“已合并”写成“已上线”。
