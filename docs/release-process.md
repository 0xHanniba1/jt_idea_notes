# 开发、验收与云端发布

## 发布边界

4184 是开发预览环境，4180 是本地验收环境，云服务器是独立的正式环境。三者各自保存数据，不自动同步。

| 触发条件 | 执行内容 | 不触发的动作 |
| --- | --- | --- |
| 提出修改需求 | 独立分支开发、测试，更新 4184 预览 | 合并 main、更新云端 |
| 明确要求“交付 main，并更新 4180” | 检查、合并 PR、同步 main、更新本地 4180，完成 Issue 和分支收尾 | 更新云端 |
| main 的 push 构建与测试成功 | 完成 CI 检查，保存供 E2E 使用的构建产物 | 发布镜像、连接服务器、更新云端 |
| 明确要求“发布到云服务器” | 确定版本，按下文执行一次受控发布 | 用本地数据库覆盖云端数据 |

日常可以多次重复“修改 → 4184 → main → 4180”。验收通过、合并 main、镜像构建成功均不等于云端发布授权。没有自动云端部署任务，也不在 Actions 中保存服务器登录凭据。

## 镜像与版本

不再使用 GHCR 自动镜像发布。CI 保留构建、单元测试、端到端测试和工作流检查；CI 镜像产物仅用于测试，不触发部署。

收到明确的云端发布指令后，按已确认的 main 提交在本地构建 `linux/amd64` 镜像，使用独立标签 `jt-idea-notes:<提交前8位>-amd64`，记录完整提交 SHA。从干净的 Git 源码构建；若复用已有前端产物，必须先核对其源码输入和产物摘要与目标提交一致。

使用 `docker save` 将镜像打包为 gzip 文件，通过现有 Workbench 文件上传传至服务器。两端校验压缩包 SHA256 一致，再执行 `docker load`；禁止将数据库、环境文件或凭据放入镜像包。镜像导入和校验在旧应用仍运行时完成，保留旧镜像供回退。

记录镜像架构、revision 标签、镜像包 SHA256、OCI manifest digest 和 config digest。不同 Docker 存储后端的 `image inspect .Id` 可能对应 manifest 或 config，须与镜像包相应字段核对，不能混用两者或跳过摘要检查。

- 应用采用 host 网络，只监听回环地址 `127.0.0.1:4180`，由 nginx 提供 HTTPS。

## 云端发布步骤

本节仅在用户明确要求更新云服务器后执行。可以提前整理版本和迁移清单，但不得由本地验收或 CI 完成自动进入本节。

1. **固定范围。** 明确目标提交、成功 CI、镜像标签和镜像包 SHA256，记录用户的发布指令。发布版本确定后，后续 main 更新不应改变本次目标。
2. **核查现场。** 读取云端当前镜像和提交、Compose、数据库版本及迁移历史、磁盘空间、应用健康和备份状态。只记录配置摘要，避免输出 `.env` 密钥。与上述历史拓扑不符时先调整计划，不盲目套用旧命令。
3. **审查迁移。** 比较云端当前版本与目标版本之间的全部迁移，明确预期数据变化、旧应用兼容性和失败恢复方式。应用镜像启动时会先执行迁移，不能把“启动新容器”当作无数据库影响的动作。
4. **准备镜像。** 本地构建、打包并上传镜像；核对上传包 SHA256 后导入，验证架构、提交元数据和镜像摘要。保留当前镜像供兼容回退；保持既有 `pull_policy: never`，不依赖注册表拉取。
5. **备份。** 暂停应用写入后运行现有备份脚本，保留数据库、Compose、环境文件及 nginx 配置，记录目录与 SHA256。验证归档可读；涉及有损迁移时，先在隔离库验证恢复及迁移。保留当前账号、密码和 JWT 密钥，不重新生成配置。
6. **更新应用。** 只将 Compose 的应用镜像改为已核验的独立本地标签，保留数据库、端口、挂载及其他运行配置。检查 Compose 配置，启动应用并监测迁移结果及健康状态；不执行删除卷或重建数据库操作。
7. **验收。** 核对实际运行提交与镜像 digest；检查 HTTPS、静态资源、登录、权限、记录和已有附件。数据对照须区分迁移预期变化与异常丢失，不能仅以 HTTP 200 或容器 healthy 判断成功。涉及真实账号的验证使用已有授权会话，不擅自重置密码或新增账号。
8. **记录。** 保存下列发布记录，将结果明确标为成功、回退或中止。成功后保留发布前备份和旧镜像，不顺手清理历史数据。

## 失败处理

- 构建、上传、导入、检查或备份失败：不启动新版本，若已暂停应用则恢复原服务。
- 数据库迁移未开始，或已确认新数据库结构与旧应用兼容：恢复原 Compose 镜像，启动旧应用并重新验收。
- 迁移已改变数据且旧应用不兼容：保持受控维护状态，记录错误与数据库状态，优先评估前向修复。不得假定换回旧镜像即可恢复。
- 恢复数据库会覆盖备份之后的新数据，不做自动恢复。先明确数据损失范围和恢复方案，取得该操作所需授权，再执行恢复并核对。

## 发布记录模板

```text
发布时间与操作者：
用户发布指令 / 目标服务器：
原提交 / 原镜像 digest：
目标提交 / CI 运行链接：
目标镜像标签 / manifest digest / config digest / 架构：
镜像包 SHA256 / 上传后校验结果：
待执行迁移 / 预期数据变化 / 旧版本兼容性：
发布前备份路径 / SHA256 / 归档与恢复验证结果：
实际运行提交 / 实际镜像 digest：
健康、登录、权限、记录与附件验收：
结果 / 未解决问题 / 回退情况：
```

发布记录不得包含密码、令牌、Cookie 或完整环境文件。仓库中的开发交付记录与实际云端发布记录分别维护，避免将“已合并”写成“已上线”。
